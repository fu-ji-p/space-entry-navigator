# 宇宙産業参画シミュレーター（Space Entry Navigator）設計仕様書

## 1. 目的・背景・設計思想

本アプリは、宇宙分野以外の企業が宇宙産業への参画を検討する際、自社の関与類型を見立て、期待便益と障壁を値踏みするための「対話型の地図」である。論文の枠組み（関与類型 D0〜D5、便益 B1〜B3、障壁 W1〜W3）を、読む資料から触って考える道具に変換する。

### 設計思想

- 予測ツールではなく思考整理ツール。数値は相対的な目安であり、精度より「どこを考えるべきか」が伝わることを優先する
- 論文の中核的主張「便益と障壁は表と裏の関係」「公的資金は踏み台」「未知の障壁（W3）は資源では越えられない」「宇宙が手段になれば必須産業になる」を、操作に対する反応として体験できるようにする
- 類型に優劣はない。D0からD5へ進むことを促す表現を避け、現在地と目標地点の差分を示すに留める
- 著者が枠組みを更新し続けられるよう、定義・マトリクス・重み・考察ルールはすべてデータファイルで管理する
- 個人名・所属・論文タイトルを表示しない。匿名の枠組みとして流通させる

## 2. 想定ユーザーとユースケース

主ユーザーは異分野企業の新規事業担当者と経営企画担当者。副ユーザーは支援機関の担当者、自治体・クラスター関係者、研究者である。

| ユーザー | 状況 | アプリで得たいもの | 主に使う機能 |
| --- | --- | --- | --- |
| 新規事業担当者 | 宇宙参画を検討し始めたが、何から考えればよいか分からない | 自社の立ち位置と、狙える便益・覚悟すべき障壁の全体像 | 類型診断、シミュレーター |
| 経営企画・役員 | 「なぜ我が社が宇宙か」を社内で説明する必要がある | 説明用の根拠と検討メモ | シミュレーター、レポート出力 |
| 支援機関・コンサル | 企業との対話で共通言語が欲しい | 枠組みの一覧と、相手企業に合わせた表示 | 探索モード、URL共有 |
| 研究者・著者 | 枠組みを対話を通じて更新したい | 編集しやすいデータ構造 | データファイル |

### 代表的な利用フロー

1. トップで免責と全体像（D・B・W の3つの軸）を30秒で把握する
2. 類型診断で「現在地」と「目指す地点」の類型を見立てる（各6問程度、3分）
3. シミュレーターで自社状況のスライダーを動かし、便益と障壁の変化を見る（5分）
4. 考察メッセージを読み、自社に当てはまる論点を選ぶ
5. レポートを Markdown でコピー、または URL で同僚に共有する

各ステップは単独でも使える。診断を飛ばしてシミュレーターで類型を直接選んでもよい。

## 3. 画面構成と機能要件

単一ページアプリで、上部タブ（または左ナビ）で5画面を切り替える。全画面の状態は URL ハッシュに保持し、リロードと共有に耐える。

| 画面 | ルート | 役割 | 主な要素 |
| --- | --- | --- | --- |
| ホーム | `#home` | 全体像と免責 | 3軸（D・B・W）の概念図、使い方、「診断を始める」「探索する」ボタン |
| 類型診断 | `#diagnose` | 現在地と目標の類型推定 | 現在地6問・目標6問、結果カード（D0〜D5）、シミュレーターへ送るボタン |
| シミュレーター | `#simulate` | 便益と障壁の可視化 | 類型セレクタ、状況スライダー、動機チェック、2つのチャート、考察メッセージ |
| 探索 | `#explore` | 枠組みの辞書 | D/B/W の全カード、便益⇔障壁の対応図、フィルタ |
| レポート | `#report` | 持ち帰り | 検討メモの生成、Markdown コピー、共有URL生成、印刷用レイアウト |

### 3.1 ホーム

- 1画面で「関与類型（6）→ 便益（3層16項目）→ 障壁（3層5項目）」の構造を図で示す
- 免責文「本ツールの結果は予測ではなく、検討の論点を整理するための地図です」を固定表示
- 出典表記は `attribution.ts` の定数を表示（初期値は匿名表記）

### 3.2 類型診断

- 現在地と目標の2パートに分け、各パートは D0〜D5 に対応する Yes/No 質問6問（第4章に質問文）
- 判定は「Yes と答えた中で最も高い類型」を基本とし、該当なしなら「未関与（D-）」とする
- 結果カードは類型の定義と例を表示し、「この見立てでシミュレーターへ」ボタンで類型を引き継ぐ
- ユーザーは結果を手動で上書きできる

### 3.3 シミュレーター（中核機能）

入力

- 現在地類型と目標類型（D-〜D5 のセレクタ2つ）
- 自社状況スライダー5本（各1〜5）: 資本余力、時間許容度、技術親和性、宇宙固有知の保有、経営層の納得度
- 動機チェック（複数選択）: 儲かる／高められる／人が育つ／強くなる／知られる／戻ってくる／社会に貢献する／使命感
- トグル2つ: 「公的支援を活用する前提か」「宇宙でしか実現できない価値があるか」

出力

- 便益チャート: 16項目の期待便益スコア（0〜100）を層別に色分けした横棒グラフ。動機に合致する項目を強調
- 障壁チャート: W1-1, W1-2, W2-1, W2-2, W3 の障壁スコア（0〜100）を横棒グラフ。「資源で越えられる」W1・W2 と「性質が異なる」W3 を視覚的に区別
- 考察メッセージ: 第5章の考察ルールに合致したものを最大5件、重要度順に表示
- 入力変更に対し即時再計算（デバウンス不要、計算は軽量）

### 3.4 探索

- D/B/W 各項目をカード表示。カードは定義、例、キャッチコピー（【儲かる】等）、関連する他項目へのリンクを持つ
- 便益⇔障壁の対応図: 論文5.1の対応（W1→B1-5、W2→B1-2・B1-3・B1-4、W3→B3-4・B2-4）を表示
- 類型で絞り込むと、その類型に関連の強い便益・障壁だけが強調される

### 3.5 レポート

- シミュレーターの入力と出力を1枚の検討メモに整形: 見立てた類型、上位便益5件、障壁5件、考察メッセージ、免責、生成日時
- 「Markdown をコピー」ボタン（クリップボード API）
- 「共有URLをコピー」ボタン（状態をハッシュに符号化、第7章参照）
- 印刷用 CSS（A4 1〜2枚に収まる）

## 4. ドメインデータ定義（D/B/W）と関連マトリクス

すべて `src/data/` 配下の TypeScript ファイルに置く。定義文は論文の記述を要約したもので、著者が自由に書き換えてよい。関連マトリクスの数値（0〜3）は論文の記述から起こした暫定案であり、第10章の確認事項とする。

## 5. シミュレーターのスコアリングロジックと考察ルール

ロジックは `src/logic/score.ts` に純粋関数として実装し、Vitest でテストする。係数はすべて `src/data/weights.ts` に置く。スコアは 0〜100 の相対値で、順位と増減の方向が伝わればよい。

### 5.1 入力の型

```typescript
type StageId = 'D-' | 'D0' | 'D1' | 'D2' | 'D3' | 'D4' | 'D5';
type Motive = 'profit' | 'tech' | 'people' | 'org' | 'brand' | 'spillover' | 'society' | 'mission';

interface SimInput {
  current: StageId;
  target: StageId;
  capital: 1 | 2 | 3 | 4 | 5;      // 資本余力
  patience: 1 | 2 | 3 | 4 | 5;     // 時間許容度
  techFit: 1 | 2 | 3 | 4 | 5;      // 技術親和性
  spaceKnow: 1 | 2 | 3 | 4 | 5;    // 宇宙固有知の保有
  conviction: 1 | 2 | 3 | 4 | 5;   // 経営層の納得度
  motives: Motive[];
  usePublicFunds: boolean;         // 公的支援を活用する前提
  spaceOnlyValue: boolean;         // 宇宙でしか実現できない価値がある
}
```

動機と便益の対応: profit→B1-1、tech→B1-2、people→B1-3、org→B1-4、brand→B1-5、spillover→B1-6、society→B3-1・B3-2・B3-3、mission→B3-4。

### 5.2 障壁スコア

各障壁 w について、目標類型の基礎障壁 `base[w][target]`（0〜3）と、対応するスライダー値 `r`（1〜5、複数なら平均）から計算する。

```latex
W_w = 100 \times \frac{base_w}{3} \times \left(1 - k_w \cdot \frac{r - 1}{4}\right) \times (1 + 0.1 \cdot gap)
```

- `gap` = 目標類型と現在地類型の段数差（D- を 0、D5 を 6 として差を取り、負なら 0）
- `k_w` は資源で下げられる割合。W1-1, W1-2, W2-1, W2-2 は 0.8、W3 は 0.4（論文5.3: 未知はレイヤーが異なり、資源では越えきれない）
- `usePublicFunds` が真なら W1-1 に 0.6 を乗じ、W1-2 に 0.85 を乗じる
- `spaceOnlyValue` が真なら W3 に 0.5 を乗じる（論文5.4: 宇宙が手段になれば参画せざるを得なくなる）

### 5.3 便益スコア

各便益 b について、目標類型の関連度 `rel[b][target]`（0〜3）を基礎とし、動機とトグルで調整する。

```latex
B_b = 100 \times \frac{rel_b}{3} \times m_b \times s_b \times p_b
```

- `m_b` = 動機係数。動機に対応する便益なら 1.25、それ以外 1.0。動機未選択なら全て 1.0
- `s_b` = 希少性係数（論文5.1「表と裏」の実装）。対応表 `pairs.ts` で障壁 w の裏側にある便益は、その障壁スコア `W_w` が高いほど増える: `s_b = 1 + 0.3 × (W_w / 100)`。それ以外は 1.0
- `p_b` = 公的資金係数（論文5.2「踏み台」の実装）。`usePublicFunds` が真なら B2-2 は 1.3、B1-5 は 0.85（壁が低くなると希少性が薄れる）。偽なら 1.0
- `spaceOnlyValue` が真なら B2-6 と B3-4 に 1.3 を乗じる
- 最終的に 100 で上限クリップする

### 5.4 考察メッセージのルール（`insights.ts`）

各ルールは条件関数と本文を持ち、条件を満たしたものを優先度順に最大5件表示する。本文は論文の考察を平易に言い換えたもので、著者が編集する前提。

| 優先度 | ID | 条件 | 本文の要旨 |
| --- | --- | --- | --- |
| 1 | unknown-high | W3 が 60 以上 | 最大の壁は資金でも技術でもなく「腹落ち」。資源を足しても下がりにくい。宇宙に取り組む理由を社内の言葉で言えるかが分かれ目 |
| 2 | mission-driven | motives に mission を含み、W3 が 40 以上 | 合理性より使命感で決めた参入は撤退理由が見えにくい。それは強みにも弱みにもなる |
| 3 | space-only | spaceOnlyValue が真 | 宇宙でしか解けない課題があるなら、宇宙は目的でなく手段になる。参画は「するか」でなく「いつか」の問いに変わる |
| 4 | scarcity | usePublicFunds が偽で W1-1 が 60 以上 | 高いコスト障壁の先には競合が少ない。越えたこと自体が「知られる」便益になる |
| 5 | stepping-stone | usePublicFunds が真 | 公的資金は壁を壊すのでなく踏み台をつくる。資金が行き渡ると希少性は薄れるので、早く越える設計が要る |
| 6 | tech-growth | W2-1 が 50 以上で、motives に tech または org を含む | 技術の壁に挑む過程で、優劣でなく独自性の高い能力が育つ。挑む企業が少ないほど独自性は高い |
| 7 | efficiency-only | target が D1 | 業務効率化が中心で定量化しにくい。それでも組織の技術探索力は高まる。次の一歩を描くかどうかを決めておく |
| 8 | big-leap | gap が 3 以上 | 一足飛びは時間・知・機会の壁が同時に立つ。中間の類型を経由する道筋も検討に値する |
| 9 | spillover-focus | motives に spillover を含み、target が D5 | 専業化すると還流先の本業がなくなる。環流を狙うなら D2〜D4 の方が整合的 |
| 10 | low-conviction | conviction が 2 以下 | 納得度が低いまま進めると、他の壁を越えても意思決定で止まる。まず「なぜ我が社か」を言語化する |
| 11 | cluster | target が D4 または D5 | 地域クラスターに近いかで参入ハードルが変わる。個社でなく地域で取り組む選択肢を確認する |
| 12 | balanced | 上記のいずれにも該当しない | 便益と障壁は表裏。障壁が低く見える類型は便益も小さくなりやすい |

### 5.5 診断ロジック（`diagnose.ts`）

- 6問の Yes/No 配列を受け取り、Yes のうち最も高い類型を返す。Yes なしは D-
- 現在地と目標の両方に同じ関数を使う
- 目標が現在地より低い場合もエラーにしない（縮小も正当な選択。gap は 0 とする）

### 5.6 テスト観点

- スライダー全て 5 で障壁が最小、全て 1 で最大になる単調性
- W3 はスライダーを最大にしても `base × 0.6` 以上残る
- usePublicFunds を真にすると W1-1 と B1-5 が下がり B2-2 が上がる
- spaceOnlyValue を真にすると W3 が下がり B2-6 が上がる
- 考察ルールの各条件が想定入力で発火する
- URL ハッシュの符号化と復号が往復で一致する

## 6. UI/UX方針

「検討の際に手軽に触れる」を最優先し、説明を読まなくても触れば分かる画面にする。

- 色の意味を固定する: 企業レベル便益＝青系、産業レベル＝緑系、社会レベル＝橙系、コスト障壁＝灰、技術障壁＝紫、意思決定障壁（W3）＝赤。W3 だけ色を変えるのは「性質が異なる」ことを示すため
- キャッチコピー（【儲かる】【腹落ちしない】等）を項目名より大きく表示する。論文の語り口がこのアプリの個性になる
- スライダーはラベル付き5段階。各段階の意味を短文で示す（例: 資本余力 1「既存予算内のみ」〜 5「数十億円規模の投資判断が可能」）。文言は `ja.ts` で編集可能
- チャートは項目をクリックすると定義カードが開く（探索画面と同じコンポーネント）
- 類型は横一列の D-〜D5 ステップ表示とし、現在地と目標を2つのマーカーで示す。矢印や「進む」という表現は使わない
- 空状態を作らない: 初期値は current=D-、target=D3、スライダー全て 3、動機なし、トグル両方オフ。開いた瞬間にチャートが描かれている
- 1画面に収める: デスクトップでは入力左・出力右の2カラム、モバイルでは入力を折りたたみパネルにし出力を上に出す
- 文章は短く、断定を避ける。「〜になり得ます」「〜が立ちやすくなります」
- 印刷とダークモードは対応するが、アニメーションは最小限（スコア変化時の棒の遷移のみ）

### URL 状態の符号化（`urlState.ts`）

- ハッシュは `#simulate?s=<base64url(JSON)>` 形式。`s` は `SimInput` を短いキー（c, t, k, p, f, s, v, m, u, o）に圧縮した JSON
- 診断の回答はハッシュに含めない（結果の類型だけが引き継がれる）
- 復号に失敗したら初期値で開き、エラーは出さない

### 配信

- `npm run build` で `dist/` を生成。GitHub Pages（`gh-pages` ブランチまたは Actions）で公開
- `vite.config.ts` の `base` は `process.env.VITE_BASE ?? '/'`
- 外部通信ゼロ。フォントは `system-ui, -apple-system, "Hiragino Sans", "Noto Sans JP", sans-serif`

## 8. 非機能要件（匿名化・アクセシビリティ・配信）

### 匿名化

- 個人名、所属組織名、論文タイトル、学会名、パネリスト情報、参考文献の著者名をコード・UI・README・コミットメッセージに含めない
- 出典は `attribution.ts` の `ATTRIBUTION_TEXT` 定数1か所のみ。初期値「本ツールは、異分野企業の宇宙産業参画に関する学術論文の分類枠組みに基づいています」
- 論文中の具体的地名（北海道・東北等のクラスター例）は B2-3 の例として残してよいが、企業名は出さない
- ビルド前に `npm run check:anon` スクリプトで禁止語リスト（著者が `scripts/anon-words.txt` に記入）を grep し、該当があれば失敗させる

### アクセシビリティ

- スライダー・トグル・チェックはネイティブ要素または WAI-ARIA 準拠。キーボードのみで全操作可能
- チャートの各棒に `aria-label` でスコアと項目名を付与し、チャート直下に同内容の表を `sr-only` で置く
- 色だけに意味を持たせない（層をラベルでも示す）。コントラスト比 4.5:1 以上

### 性能・互換

- 初回ロード 300KB（gzip）以下を目標。Recharts はツリーシェイク
- 対応ブラウザは直近2年の Chrome / Safari / Edge / Firefox
- オフラインでも動作（外部通信なし）

### プライバシー

- 入力内容はサーバーに送らない。URL共有は利用者の明示操作のみ
- アナリティクスは入れない。必要なら後から `config/` に差し込める構造にする
